# tunnel-forward.sh 完整功能审查

这是修复前的历史审查。下列六项问题均已在后续版本修复，修复及双机验证结果见 [完整验证记录](verification-full-2026-10-24.md)。

审查对象为上轮修复后的 1464 行脚本，SHA-256：`dd5417ce153dfee11bbb004c113e0c77bceb8fc5476ed7e7171be1bd41290901`。覆盖 GRE 创建、持久化和删除，普通端口转发、DNS、服务安装，以及 GRE nftables 配置、过滤、重载和回滚。

本轮未修改脚本或生产配置，未连接生产服务器。按个人运维脚本的使用规模审查，包含两个管理终端同时操作的情况。以下六项均有复现证据；故障注入使用隔离容器和命令 mock，路由与规则正常路径使用隔离 Linux 内核。

## 1. [P1] GRE 转发成功提示不代表使用了所选隧道

位置：`tunnel-forward.sh:1077`、`tunnel-forward.sh:1223`。

DNAT 只改变目标 IP，实际出口由路由表决定。脚本没有确认到对端地址的路由使用所选隧道，但 SNAT、过滤和 MSS 规则却限定了这个隧道。

触发示例：创建两条隧道 A、B，均使用默认的 `10.10.1.1/24`，随后选择 B 将端口转发至 `10.10.1.2`。系统路由可能仍指向 A。使用 `/32` 的隧道地址但没有对端主机路由，也可能使流量走默认出口。

隔离环境用两个 dummy 接口验证实际路由选择，配置校验仍接受错误出口的记录：

```text
selected=tfrouteB validation=accepted
10.231.17.2 dev tfrouteA src 10.231.17.1
```

影响：默认 DROP 时转发失败；默认 ACCEPT 时可能走另一条隧道，且没有命中所选接口上的 SNAT。

最小修复：提交前校验到 peer 的实际出口接口，冲突时拒绝并说明需要修正网段或路由。如果要支持相同 peer 经不同隧道，需增加明确的策略路由。

## 2. [P2] 普通服务重装失败会停掉原本健康的后台进程

位置：`tunnel-forward.sh:905`；添加规则会在 `tunnel-forward.sh:802` 调用这个安装流程。

安装先停止服务，再同步规则。若此时规则预检或应用临时失败，函数直接返回，没有恢复原来正常运行的服务。systemd 的 `Restart=always` 不会撤销显式的 stop。

在隔离环境令同步步骤返回失败，实际控制流程输出：

```text
stop tunnel-forward.service
failed-sync
result=1 running_after=no
```

影响：已有内核规则可能继续转发，但 DNS 自动更新和规则自动恢复的后台进程停止。无需升级脚本，普通新增规则也可能触发。

最小修复：记录原服务状态和版本；安装失败时恢复已知安全的原服务。对会破坏新规则的旧版服务单独处理，不应把所有版本都永久停止。

## 3. [P2] GRE 安装失败的回滚遗漏了服务文件

位置：`tunnel-forward.sh:1154`、`tunnel-forward.sh:1172`、`tunnel-forward.sh:1317`。

安装直接覆盖 `load-gre-forward.sh` 和 `tunnel-gre-nft.service`。如果写文件或后续安装步骤失败，回滚只恢复 nft/filter 配置和实时规则，没有恢复 loader 和 unit。

故障注入在覆盖旧 unit 后模拟写入失败，得到：

```text
rebuild_status=1
nft_file_after=OLD-NFT
filter_file_after=OLD-FILTER
unit_after=[Unit]
unit_restored=no
```

影响：提示已回滚后，实时转发可以仍然正常，但旧的开机服务文件已经损坏，下次重启或重新加载服务时失效。

最小修复：loader 和 unit 同样先写临时文件，并与其余持久化文件一起备份、原子替换和回滚。

## 4. [P2] 并发创建 GRE 会覆盖隧道管理记录

位置：`tunnel-forward.sh:308`。

创建函数对 `tunnels.conf` 的读取、追加和替换没有加共享锁，而删除和转发配置会使用 `forward.lock`。

用两个并发创建操作在读取旧配置后同步继续，输出：

```text
statuses=0,0; records=1
```

影响：两个操作都报告成功，但管理文件只保留一条隧道记录。内核中的两个接口仍存在；这项证据不代表接口或独立持久化文件同时丢失。

最小修复：交互输入留在锁外，创建与记录提交使用同一个共享锁，至少对记录的整个读改写过程加锁。

## 5. [P3] 配置末行没有换行时，菜单漏掉已生效规则

位置：`tunnel-forward.sh:818`、`tunnel-forward.sh:844`。

后台解析支持无末尾换行的配置；配置列表和编号删除循环不支持。以 `printf '8080>192.0.2.1:8080' > forward.conf` 写入后：

```text
daemon-config=8080>192.0.2.1:8080|192.0.2.1
错误: 未找到匹配的规则
delete-result=1
```

影响：配置列表漏掉最后一条，无法按编号选中删除。底部的实时 iptables 表仍可显示它，使用 `p:8080` 仍能定位删除，因此不能把这项描述为完全不可删除。

最小修复：两个读取循环均补上 `|| [[ -n "$line" ]]`，与后台解析保持一致。

## 6. [P3] 接口名称会干扰 GRE 类型识别

位置：`tunnel-forward.sh:192`。

类型识别在整段 `ip -d link` 输出中搜索 `ip6gre`，会把名称也当成类型。合法的 IPv4 GRE 接口名 `ip6gre-test` 可触发：

```text
actual=gre reported=ip6gre
```

影响：状态页、隧道选择页显示错误类型。当前调用点主要用于展示，未发现因此使用错误的创建或删除命令。

最小修复：只解析实际接口类型字段，避免对包含接口名称的整段文本做子串匹配。

## 已验证通过的路径

- Bash 语法和 ShellCheck error/warning 检查。
- 现有自动持久化回归测试，包括安装失败提示、进程替换加载、独立后台脚本运行和生成结果一致性。
- 在真实隔离 netfilter 内核中应用普通单端口、同号范围和偏移范围。
- 在真实隔离 netfilter 内核中应用 GRE 单端口与范围混合规则，并重复加载，未追加重复规则。
- 删除最后一条 GRE 规则后配置可正常加载。
- 上述操作保留了测试用第三方 NAT/过滤规则及 FORWARD 的 DROP 策略。
- 典型 IPv6 完整、压缩和 IPv4 嵌入格式校验。
- 核对 Linux 6.12 实现后，MSS `set rt mtu` 没有增大原 MSS 的问题：内核会同时考虑正反向路由 MTU，并拒绝把较小的已有 MSS 改大。

## 条件风险与验证范围

GRE 开机 loader 没有像普通 daemon 一样重新开启并检查 `net.ipv4.ip_forward`。如果已有排序更后的 `99-*.conf` 把它设为 0，可能覆盖脚本的 `90-tunnel-forward.conf`，使 GRE 重启后无法转发。这是条件性的配置冲突，本轮没有把它算入六项已复现缺陷。

本轮没有再次重启生产服务器，也没有做真实 IPv4/IPv6 GRE 两端数据传输。隔离容器缺少可用的 GRE 内核设备，因此路由选择使用 dummy 接口验证；nftables/iptables 规则则使用真实内核应用。networkd/ifupdown 的整机重启恢复也未完成验证。上轮生产验证覆盖普通转发及真实 Shadowsocks TCP/UDP 业务，不等同于完整 GRE 验证。

建议先修复第 1–4 项，再补充对应回归；第 5–6 项可一并做小修复。
